# Bounded queue comparison: 2M events

Command ran in the optimized Windows build, 2,000,000 offered events at 1,000,000/s, capacity 65,536, three trials, with 50,000-event warmup. These are local synthetic payload/checksum results, not IBKR feed measurements.

| Queue | Trial | Completed/s | Loss check | p50 ns | p95 ns | p99 ns | Max ns |
|---|---:|---:|---|---:|---:|---:|---:|
| sync_channel | 1 | 998,286 | true | 500 | 27,800 | 231,800 | 1,062,600 |
| sync_channel | 2 | 997,802 | true | 500 | 4,500 | 220,200 | 449,600 |
| sync_channel | 3 | 998,308 | true | 500 | 17,700 | 241,500 | 554,900 |
| rtrb SPSC | 1 | 998,705 | true | 0 | 74,500 | 281,500 | 978,500 |
| rtrb SPSC | 2 | 998,851 | true | 0 | 61,000 | 264,100 | 944,600 |
| rtrb SPSC | 3 | 998,726 | true | 0 | 76,000 | 283,500 | 1,080,800 |

The SPSC ring did not improve this machine's throughput or tail latency enough to justify replacing the original as the default. Neither implementation meets the 10 microsecond p99 goal. The single-thread Windows schedule and current open-loop harness are material limitations. Follow-up: run release trials on the intended Linux target with producer/consumer pinned to separate physical cores, then add consumer work incrementally (decode, book update, log write) and retain raw rows. The SPSC generator's 0 ns p50 means events can be consumed before their nominal scheduled deadline and the reported latency clamps negative values to zero; revise the harness to report producer lateness and queue residence separately before making a p50 claim.
